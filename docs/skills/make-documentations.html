Make Documentations

Docs that describe the code as it is. Propel asks before it writes a page. Pages are written in one style, checked mechanically by doc-check.sh, and compared with the code by a second model before you see them.

The Docs State the Present

Versioned docs hold the current design, results and status. History stays in scratch/: a page may say that history exists outside version control, but it never links into it and never copies text from it. Unbuilt work appears only as “To build: …”.

Overview

Make Documentations writes and updates a project's README, hub, section index pages, component and method pages, results write-ups and runbooks. It is active in all four modes. Its automatic triggers never write a page without your answer: each one asks a single question first, and /disable-make-documentations turns those questions off. Each page it writes goes through Concise and doc-check.sh; a page changed by more than a trivial edit then gets a Codex Docs fidelity consult (skipped, with one line, when Codex is off or unavailable) that names every claim the code contradicts or does not support. The skill writes pages to disk and never commits them.

When It Triggers

An explicit request writes. Every automatic trigger asks first.

TriggerDetails
Manual"document this", "write the docs", "update the docs", "make documentation", "write a results page", "document the results", "write a runbook", "docs are stale". Skips the question about whether to write; if the scope is unclear, it asks which pages
After Gate 3Implementation: when a component's audits pass and docs pages reference the changed files, the docs question rides in the same question box as Gate 3

After a retrospectiveRetrospective: when the entry changes what a results or runbook page states, the docs question is asked; if the fold-in question is asked at the same moment, it rides in the same question box

It Asks Before Writing

Each automatic trigger leads to one question in Claude Code's question UI, and no page is written until you answer it. The question names every page that would be created or updated and what each would cover. For example:

Docs: 2 pages cover what this change touched.
  docs/methods/<component>.md  the new <input> and its shape
  docs/results/<study>.md      the headline number after this change

  1. Update all 2 pages
  2. Update only docs/methods/<component>.md
  3. Skip this time
  4. Stop asking (same as /disable-make-documentations)
AnswerWhat happens
Update all N pagesWrites every named page, then runs the procedure: Concise, doc-check.sh, the Docs fidelity consult, and the pages are presented
Update only the most important pageThe same, for that one page
Skip this timeNo page is written
Stop askingSame as /disable-make-documentations: no page is written, and Propel stops asking about docs in this project until you turn the prompts back on

When a gate question is asked at the same moment, the docs question rides in the same question box, so one round of answers covers both. Only “Update all” or “Update only” writes a page.

An explicit request (“document this”, “write the docs”) skips the question about whether to write, because the request already answers it. If the request leaves the scope unclear, the one question is which pages.

Turning the Prompts Off

CommandEffect
/disable-make-documentationsWrites {"enabled": false} to .propel/docs.json. Propel never asks about docs or documents automatically until the prompts are turned back on
/enable-make-documentationsWrites {"enabled": true} to .propel/docs.json. The automatic triggers ask again

The setting belongs to the project and persists across conversations, like /disable-codex. While it is off:

  • the auditor-dispatch hook adds no [propel:docs] line;
  • the per-turn routing card from route.sh shows a docs prompts: off line, so the model stays quiet about docs;
  • the first trigger in a session prints one line: ◇ Docs prompts off — /enable-make-documentations to turn them back on.
  • an explicit request for docs still works.

Off values follow the Codex rule: the prompts are off when enabled is false, null or 0, or a string that, trimmed and lowercased, is "false", "0", "off", "no" or empty. A missing file means on.

The Style Contract

#Rule
1Two layers. Docs hold the present; scratch/ holds history. No links into scratch/.
2Layered entry points. README → hub → section index pages (a paragraph and a Page | Question table) → leaf pages, one per component, method, dataset, metric, results write-up or runbook.
3One leaf anatomy. H1 “Name: essence”, a 3-6 sentence overview, 3-8 noun- or question-named sections, optional known limits, references, and a dated Status with a 2-3 sentence Why this design at the bottom.
4A choice carries its reason as a consequence: “<choice>, so that <inference>; a failure would mean <x>, not <y>.”
5No number stands alone. Its baseline, floor or ceiling sits beside it, with n, seeds and interval status.
6Calibrated claims. Observation first, then “our reading is”. Study-wide limits go in the README and hub too.
7Checkable code fidelity. Resolving relative links, backticked paths and function names in a “Code:” paragraph, named tests, docstrings that link back. No line numbers.
8Config pages show an annotated tree, one config in full, a key table, what raises instead of defaulting, drift between code defaults and recorded runs, and a precedence rule.
9Shapes inline as [B, T, D] where a tensor is transformed; a silent pitfall is named with the assertion that guards it.
10Results pages read like short papers: numbered questions, claim-stating headings, one captioned figure per claim, a shared “How to read the figures” block, a numbered discussion.
11Plain tone. First person plural, no emoji, no marketing, no TODO/TBD, ASCII diagrams; a superseded design gets one sentence.

The skill carries a template for each page type, with generic placeholders only.

PageWhat it holds
Project READMEWhat the project is and its main result beside a baseline, study-wide limits, where to start, a quick start, a dated status

The Procedure

  1. Find the docs root: an existing docs/ or documentation/, otherwise the README. If there is none, one question: create docs/ with a hub page, or keep it to a README section, with what each costs.
  2. Pick the pages: the one you asked for, or the pages that cover the changed files.
  3. Ask, unless you asked: on an automatic trigger, the docs question; the procedure continues only after “Update all” or “Update only”. An explicit request skips it, or asks which pages when its scope is unclear.
  4. Write or update them from the templates: present tense, no scratch/ paths, code paths in a “Code:” paragraph, the dated Status and Why this design rewritten together with the body.
  5. Run Concise on each page: save the draft, rewrite, check with claim-check.sh.
  6. Run doc-check.sh on the pages and fix every line it prints.
  7. Docs fidelity consult when a page changed by more than a trivial edit (see below).
  8. Present the pages with the fidelity card. You accept them or edit them.

doc-check.sh

A bash-and-awk script (no python3, no network), run from the repo root:

bash .claude/scripts/doc-check.sh [--root DIR] FILE...
KindReported when
linkA relative link's target does not exist (resolved from the page's directory; a leading / from the root)
anchorA #anchor into a .md page matches none of its headings, slugged GitHub-style
pathA backticked repo path (contains /, ends in a file extension or /) does not exist under the root
scratchAny link, backticked path or bare path into scratch/
markerTODO, TBD or FIXME as a word
emojiAny emoji
statusA leaf page (anything but README.md and index.md) has no Status line with a YYYY-MM-DD date

Each problem is one line, FILE:LINE: KIND: DETAIL. Fenced code blocks are exempt from every check except emoji. Exit 0 means clean, 1 means problems were found, 2 is a usage error.

The Docs Fidelity Consult

The last step is a Codex consult, announced like every other, with two questions in one call:

  • “Here are the doc pages at <paths> and the code they describe. Name every claim the code contradicts or does not support, by page and heading, or say 'no additional findings'.”
  • The writeup-review question, comparing each page's draft with its rewrite. This call counts as the writeup review for those pages.

Both questions pass paths, which Codex reads itself, so the consult is skipped (and Claude says so) if a page or the code holds secrets, credentials or unpublished data. It never fires for scratch/ or a trivial edit. Findings come back verified and attributed; see Codex Consult.

Guardrails

GuardrailWhy
Never write a page on an automatic trigger without an answerWhich pages change is your decision; the trigger only finds the pages that may be stale.
Never document unbuilt work, except as “To build: …”A page that describes a plan as if it were code is the drift this skill exists to prevent.
Never copy text from scratch/History is written for the session it came from; the docs restate the present from the code.
A superseded design gets one sentenceThe current design stays readable; version history holds the rest.
Rewrite Status and Why this design with the bodyA Status box that drifts from the body is the style's most common failure.
Never present a page whose doc-check.sh run did not exit 0Broken links and missing paths are cheap to find mechanically.
Never commitPages are written to disk; what goes into version control is your decision.
