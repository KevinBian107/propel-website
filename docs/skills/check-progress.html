Check Progress

One read of the task ledger, shown as-is: which training runs, plan tasks and monitor loops are still open, and which of them need a decision. Read-only — every state change is the user's call.

Information, Not a Decision

The skill never restarts a job, never kills one, never edits code, and never changes a task's state without the user's answer. It shows the table, names what needs attention, and asks. If you want a run supervised until it finishes, that's Monitor; if you want it relaunched, that's Trainer Mode.

Overview

Work that outlives a turn — a training run in screen, an implementation task from an approved plan, a monitor loop — is recorded in a per-session ledger, .propel/tasks/<session>.jsonl. The ledger is written only by scripts/task-queue.sh, not by the model, so a task Claude claims to have started but never recorded simply isn't there. Check Progress is how you read it. It is active in all four modes.

When It Triggers

TriggerDetails
Manual"check progress", "what's running", "status of my jobs", "what's left", "where was I", "is my training done", "did my run finish"
ContextualThe session starts with open tasks from an earlier session and your first message is about continuing ("let's continue", "pick up where we left off")
PromptedEvery turn with open tasks, route.sh adds one line: tasks: N open in this session, M from earlier sessions — run check-progress

Step 1 — Show the Table

One script call, printed unchanged — no reordering, summarizing or dropped rows. It lists every open task, plus finished tasks from the last 10 session files written within 14 days:

bash .claude/scripts/task-queue.sh list --table --sessions 10
| ID | Task | Kind | Status | Progress | Started | Session |
|---|---|---|---|---|---|---|
| t261118-193056-fd4d | watch sweep | monitor | running |  | 11-18 19:30Z | s2 (this) |
| t261118-193056-7a8c | ppo baseline seed 0 | train | lost |  | 11-18 19:30Z | s1 |

In the Session column, (this) is the current session, (carried here) was carried into it, and an unmarked row belongs to an earlier session. Open tasks are always listed, however old. If the script exits 5, part of the ledger couldn't be read: the table is partial (even when it says "No tasks recorded."), and the skill shows it and quotes the error line.

Statuses

A task's status is recorded by the script, and for training runs it is derived from evidence — never "running" just because nobody said otherwise:

StatusMeaning
runningRecorded as running; for a train task, its screen/tmux session is alive
done / failedFinished. For a train task, read from the run's exit file (.propel/runs/<NAME>.exit: 0 is done, anything else failed) and recorded on read
blockedThe goal wasn't met and someone has to choose the next step
lostTrain task whose session is gone with no exit file (killed, node rebooted)
unknownTrain task with no evidence either way: no exit file, and no screen/tmux session name recorded (or neither tool installed to check it)
abandonedClosed by the user's decision; it no longer appears at session start

Open means running, blocked, lost or unknown.

Step 2 — Flag What Needs a Decision

In at most three lines, the skill names the ids that are lost, unknown, failed or blocked, skipping any status with no rows — or says "Nothing needs a decision." For a train task, the log path comes from the task's start event in .propel/tasks/*.jsonl; that is where to look first for a lost or failed run.

Step 3 — Earlier-Session Tasks: Ask, Don't Act

The tasks part of the SessionStart hook lists open tasks at the start of every session (at most 20 rows). Tasks from an earlier session are shown and asked about, never changed automatically. Check Progress asks one disjunctive question per batch:

ChoiceWhat it does
Carrytask-queue.sh carry ID — resume here; the task shows as (carried here) and this session owns the follow-up. Offered only when this session's id is known (PROPEL_SESSION is set); otherwise the choice is abandon or leave open
Abandontask-queue.sh abandon ID --note "<why>" — close it for good. Nothing is killed, but the record stops prompting anyone
Leave openNo change. It appears at every session start until someone decides

No answer means leave open. Only the ids the user named are touched. If a carry or abandon finds the ledger busy (exit 3), the skill says so and offers a retry.

In the Terminal

Outside Claude, propel tasks reads the same ledger. By default it shows open tasks only; --all adds finished ones:

propel tasks                  # open tasks: running, blocked, lost, unknown
propel tasks --all            # plus finished tasks (done, failed, abandoned)
propel tasks --all --sessions N   # finished tasks from the last N session files (default 10), within 14 days

Open tasks always show, whatever --sessions says.

Guardrails

GuardrailWhy
Print the table unchangedA summary is a second claim on top of the evidence; the table is the evidence.
Never carry or abandon without the user's answerWhat an unfinished run means is a judgment, not bookkeeping.
Never restart, relaunch or kill anythingRelaunching is Trainer Mode's job, behind its own confirmation.
Never run task-queue.sh unlock unpromptedThe lock is never cleared automatically; unlock is a manual recovery the user asks for.
Partial read (exit 5): show what was read and quote the errorAn incomplete table, labelled as incomplete, beats a silent gap.
